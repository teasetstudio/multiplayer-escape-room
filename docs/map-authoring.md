# Authoring the Twin Vaults in Tiled

Open `packages/shared/src/maps/twin-vaults.json` directly in [Tiled](https://www.mapeditor.org/). It is both the original editable map and the runtime JSON source: no separate generated copy can get out of date. Keep `assets/stone-tiles.svg` beside it at the referenced relative path. The atlas contains three original geometric floor tiles; walls and objects are rectangle objects with custom classes and properties.

The active map has two 12 × 12 tile chambers sharing an impassable divider. Each has an alcove with a closed gate, a crate, pillars and ten spawn points. The original `stone-hall.json` remains an example of the earlier map format.

## Supported format

- Orientation **Isometric**, finite map, **64 × 32** tile size.
- One embedded three-tile tileset, first GID 1; uncompressed JSON arrays, no flipped tiles.
- Seven zero-offset layers with the exact names below. Object layers use unrotated rectangles; spawn objects are points.
- Runtime visuals are generated by Phaser, using floor GIDs 1–3 and the supported object classes. Replacing the editor image alone does not change runtime artwork.
- No infinite chunks, groups, external tilesets/templates, polygons, ellipses, rotations, or staggered maps. Unsupported required geometry is rejected; do not add these features without extending and testing the loader.

| Layer         | Tiled type   | Contents                                                                           |
| ------------- | ------------ | ---------------------------------------------------------------------------------- |
| `Ground`      | Tile layer   | 0 for empty visual space; GIDs 1–3 for stone floor variations                      |
| `Rooms`       | Object layer | Tile-aligned rectangles with unique IDs, `displayName` and an optional `startTeam` |
| `Walls`       | Object layer | Named rectangles with class `wall` and numeric `elevation`                         |
| `Decorations` | Object layer | Non-solid rectangles with class `rug`, elevation 0                                 |
| `Objects`     | Object layer | Named rectangles with class `crate`, `pillar`, or `door`                           |
| `Collision`   | Object layer | Explicit solid rectangles with class `wall`, `obstacle`, `boundary`, or `door`     |
| `SpawnPoints` | Object layer | Point objects marking the character's feet                                         |

The Rooms, Collision and SpawnPoints layers start hidden for editing convenience. Layer/object visibility is an editor aid; it does not enable/disable gameplay geometry. Floor painting and collision editing are **separate operations**: removing a floor tile does not automatically block that space. Add `boundary` collision rectangles over void regions. Keep visual wall/crate footprints aligned with explicit collision rectangles.

Each door's visual object name is its stable ID, for example `room-a-gate`. Its matching `Collision` rectangle has class `door` and a string custom property `doorId` with that ID. The footprints must match exactly and there must be exactly one collision shape per door. Do not also put an unconditional wall/boundary collision over the same doorway. Every room initializes the door as `closed`; there is no user interaction to change it yet.

Each room has a stable `room-…` name. Assign exactly one room to each starting team with `startTeam` set to `A` or `B`. Additional rooms can omit this property. Room rectangles must follow tile edges and have disjoint interiors. Keep each visual object entirely inside one room. Each half of the central divider belongs to its own room, so a phone can draw its boundary independently. A spawn point belongs to the room containing its whole player footprint.

## Coordinate conventions

Tiled stores isometric rectangle and point coordinates on **unprojected axes measured in tile-height units**. Here a Tiled tile is 32 object units on each axis. The loader multiplies object `x`, `y`, `width`, and `height` by **2**, yielding 64 logical units per tile. Never enter projected diamond screen coordinates as collision/spawn coordinates.

For example, a Tiled rectangle at `(128, 256)` with size `(32, 32)` becomes a logical rectangle at `(256, 512)` with size `(64, 64)`. A point at `(144, 160)` spawns feet at logical `(288, 320)`. `elevation` is a visual height in projected pixels (walls 40–42, pillars up to 58); it never changes the collision plane.

The origin is the top corner of the isometric grid. Logical X projects down-right; logical Y projects down-left. Projection, inverse projection, tile conversions, and screen-input conversion are centralized in `packages/shared/src/world/projection.ts`.

## Safe edits and another map

1. Save the JSON with its embedded tileset. Retain string map properties `mapId`, `displayName`, and `revision`.
2. Paint floors; add matching visual objects and explicit collision/void rectangles. Door IDs and object names must be unique.
3. Place at least ten spawn points in each starting room with clear 28 × 28 logical-unit footprints and enough separation. Keep them in accessible areas.
4. Run `pnpm typecheck`, `pnpm test`, and `pnpm build`. The tests validate the sample map, spawns, and team confinement; update sample-specific expectations intentionally when redesigning it.
5. Inspect host overview and player camera, including wall occlusion, corners, narrow doorways, and joystick direction. Repeat the real-phone checklist before a group session.

To introduce a different map later, add its editable JSON/assets beside this map and call `loadTiledMap` from the shared map entry. Select the same map on server and client; any future registry should resolve server-issued map IDs. No networking changes are needed for static geometry. Rebuild both applications together: the version includes a deterministic fingerprint of the entire JSON, so even an accidental stale client is detected. Each running session currently uses one map for its lifetime.

Long wall rectangles are split into tile-sized visual pieces at load time for depth sorting; collision uses the authored rectangles directly. Use small footprints for tall complex decorations. Very large/overhanging objects will require more advanced occlusion than the current base-anchor sorting.
